# Figma Harness plugin

`@figma-harness/plugin` is the Figma development plugin. It builds the active app and its design system into three owned pages, and exposes the offline harness API. The reviewed Figma document is the visual source of truth; this package, with the design system and the app it composes, is the deterministic source that rebuilds it.

## Layout

```text
manifest.json         the Figma manifest (no network access)
ui.html               the plugin window
code.js               the bundle Figma loads; generated by pnpm build or pnpm use
types/                the two modules the build resolves to the active app and design system
src/
├── entry.ts          bundle entry: the commands and HARNESS_API
├── composition.ts    the active app and its design system, through build aliases
├── main.ts           UI commands and build orchestration
├── screen-refresh.ts refreshing one selected screen in place
├── harness-api.ts    what the offline harness may read, and the CONTRACT
└── document/
    ├── workspace.ts      the three owned pages
    ├── builders.ts       page builders and canvas layout
    ├── screen-catalog.ts durable screen identity for refreshes
    ├── prototype.ts      wiring the app's flows with the design system's motion
    └── contract.ts       the document audit contract, assembled from both
tests/                the plugin workflow and document assembly
```

## Invariants

- `src/entry.ts` is the sole bundle entry, and every module of every bundled package must be reachable from it.
- The plugin depends on no app and no design system. `src/composition.ts` imports `@figma-harness/active-app` and `@figma-harness/active-design-system`, which the build resolves to the app `figma-harness.config.json` names and to that app's design system.
- `code.js` is generated. Never edit it by hand.
- Each app keeps its reviewed signatures in its own `baselines/` folder, written only by a `BASELINE_ACCEPTANCE` task. A structural refactor must leave them unchanged.
- The plugin's tests build the app template, so they pass whichever app is active.
- `ui.html` and `manifest.json` are part of the document signature.

## Generated document

- `01 · Screens`: the app's screens, grouped as it declares them, wired as a clickable prototype.
- `02 · Design system`: the design system's sheets, in its group order.
- `03 · Design lab`: an empty slot between disposable experiments.

The document signature protects Screens, Design system, shared variables and styles, the plugin UI and the manifest, and requires all three page names in order. It excludes Design lab contents, which the audits still traverse.

## In Figma

Run `pnpm build` (or `pnpm use <app>` to switch apps), then import `manifest.json` as a development plugin in Figma Desktop (**Plugins → Development → Import plugin from manifest**). Use a disposable file: the plugin replaces the contents of the pages it owns. Release validation follows the [native Figma Desktop gate](../docs/ia/ACCEPTANCE_GATES.md#native-figma-desktop-gate).

For normal iteration, select a generated screen or one of its layers and use **Refresh selected screen**. It keeps the top-level frame ID, regenerates only its contents, rewires and reads back only the interactions that screen owns, and checks that frame. The page actions replace one owned page; **Rebuild everything** is the complete integration check. A Screens build clones reaction-free repeated subtrees and closes the reuse session before attaching prototype reactions. The status reports the total duration, the native clone duration, and, when content already existed, the number and removal time of cleared top-level nodes.

What the harness proves about this output, and every command, is described in the [harness README](../packages/harness/README.md).
